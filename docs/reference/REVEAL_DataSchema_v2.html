Data Schema

The unified record the whole application reads and writes — every field captured per student, per report instance, per module and task, plus the derived layer the report is generated from. This is the spine an engineer builds against.

Orientation

Three principles before the fields

1 · A student has many report instances over time. REVEAL is re-run; each run is a dated snapshot, and comparing snapshots is how the "model has moved" story works. So the top object isn't a report — it's a student who owns an array of report_instances.

2 · Raw capture is stored separately from derived results. Everything the student does lands in raw_capture untouched. The scoring engine reads raw and writes derived. Keeping them apart means you can re-run the engine on old raw data when the scoring changes — without re-collecting anything.

3 · The trait is the central unit. Both channels write per-trait signals into a common structure; the engine scores per trait; the report renders per trait. Get the trait list right and everything else hangs off it.

// shape, top level
student
 └─ report_instances[]            // many, dated — enables drift
     ├─ raw_capture
     │   ├─ channel_a            // A1–A7 stated modules
     │   ├─ channel_b            // B1–B8 task exports
     │   └─ portfolio            // inventory + resume
     ├─ derived                  // engine output, re-computable
     │   ├─ trait_scores[]
     │   ├─ gap[] · coherence
     │   ├─ surprises[] · recurring_roles[]
     │   └─ differentiation_statement
     └─ report_payload           // optional: per-section render data

Entity 3

raw_capture.channel_a

One key per stated module. Each stores the student's answers AND the normalised per-trait score the engine derived from them.
KeyShape
a1_capacities{ items:[{prompt_id, chosen_capacity, ms}], score:{empathy, analytical, aesthetic, systems_sensing, narrative, conviction} } // each 0–1 · normalised by appearances, not item count
a2_roles{ project_tags:{project_id:[role]}, direct_pick:[role,role], score:{role:0–1} }
a3_values{ ranked:[value×12], never_compromise:{value, why}, score:{value:0–1} }
a4_conditions{ thrive:[condition], drain:[condition], best_when, stuck_when }
a5_encounters{ logs:[{what, why, feeling, themes:[theme]}], score:{theme:freq} }
a6_obsessions{ topics:[topic], saves_reads_watches:text, admired:[{name, why}] }
a7_aspiration{ desired_skills_ranked:[skill], desired_levels:{capability:0–1}, desired_impact, desired_environment, future_self_text, admired_refs:[], perceived_market_rank:[{field, rank}], direction_market_stance:enum[aligned, slightly_apart, opposed] }
Enums to freeze: capacity (6 · empathy, analytical, aesthetic, systems_sensing, narrative, conviction), capability (12 · design_research, field_research, framing, ideation, prototyping, craft_execution, visual_comm, material_media, functional_usability, systems_service, facilitation, venture), role (7), value (12), theme (~7), condition (~20). Defined once as constants so the whole app stays consistent. Craft moved from capacity → capability.

Entity 5

raw_capture.portfolio

FieldShape
projects[]{ project_id, title, domain, initiated:enum[self,assigned], group:enum[solo,group], artefacts:{research:bool, process:bool, final:bool}, individual_contribution:text, roles:[role], commercial_impact_self_tag:-1..1, noticed_unasked:text }
resume{ uploaded:bool, file_ref, parsed_frame:enum[commercial, impact, mixed, unknown] }

Factual fields (title, domain, initiated, group, artefacts) are captured first as warm-up; interpretive fields (contribution, roles, self-tag, noticed_unasked) are captured after Channel B; resume is uploaded last.

Entity 6

derived

Written by the scoring engine. Fully re-computable from raw_capture — never hand-edited.

derived.trait_scores[]

FieldTypeNotes
traitenumcapacity (6) / capability (12) / role / value / condition / salience / obsession / aspiration item
a_score · b_score0–1From channel_a module · weighted mean of tagged B-tasks (●1.0 / ○0.5)
b_situations_agreeintCount of B-situations pointing the same way as A
confidenceenumCC3 · CC2 · contradicted · surprise
evidence[]array{ source_module, channel:A|B, detail } — feeds the report's inline tags

derived.gap[] · coherence · surprises[] · recurring_roles[]

FieldShape
gap[]{ capability, current_demonstrated:0–1, desired:0–1, stated_gap:0–1, revealed_gap:0–1, classification:enum[real, performed, latent] }
coherence{ contradiction:bool, resume_frame, work_frame, adjudicated_truth:enum[work, resume], basis:[task] }
surprises[]{ trait, b_score, situations:int, confirm_question:text, confirmed:bool|null }
recurring_roles[]{ role, frequency:0–1, tier:enum[demonstrated, emerging] }
market_tension{ intrinsic_dir, market_dir, perceived_stance, market_gap:0–1, classification:enum[aligned, drifting_to_market, holding_to_pull] } // from B5 pays-best + A7 perceived-market
differentiation_statementtext — generated by the synthesis layer
Gap-source rule (important): the gap is measured on capabilities (learnable skills, A7), not capacities (innate leanings, A1) — they're different lists. So the current side comes from portfolio-demonstrated capability (which projects evidence which skills) plus Channel B, never from a self-rating; the desired side comes from A7. current_demonstrated is therefore derived from portfolio.projects[], not from channel_a.a1. Honest by construction: current = what you've shown, not what you claim.

    "differentiation_statement": "…generated…"
  }
}
The one rule that keeps it sane: nothing writes to derived except the scoring engine, and the engine only reads raw_capture. That single boundary is what makes the whole system re-runnable, debuggable, and honest — if a finding looks wrong, you can trace it straight back to the raw choices that produced it.
